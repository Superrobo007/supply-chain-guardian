Supply Chain Guardian Explained
Technical explainer · Bosch BGSW × Amrita hackathon · Problem statement 1

Supply Chain Guardian

A system that reads every ingredient your application is built from, checks each one against what the world knows about bad ingredients, works out which problems actually matter for this app, proposes a safe fix, and proves the fix works before a human signs off.

The idea in one minute

Modern software is mostly assembled, not written. Juice Shop's own code is a few thousand files, but it ships with 2,111 third-party packages written by strangers. Only 161 of them were chosen on purpose. The other 1,950 came along because a chosen package needed them, and those needed others.

Think of a restaurant. The chef picks 161 suppliers. Those suppliers buy from 1,950 others the chef has never heard of. When one far-off farm has a contamination recall, the chef needs to know three things fast: did any of it end up in my kitchen, is it in a dish I actually serve, and what do I swap it for without ruining the recipe? The Guardian does that for software.

The brief from Bosch asks for five capabilities: Discover → Detect → Analyze → Remediate → Validate. The Guardian implements each as a separate stage. One design rule runs through all of them:

Plain code collects every fact. The AI only reasons about facts the code has already recorded, and must cite them. A human makes every decision that changes anything.

Architecture

Read it as a snake. Top row: the code works out what is in the app and what looks wrong. Middle: a shared notebook of facts (the evidence ledger), which the AI agents read from. Bottom row, right to left: a proposed fix passes a policy check and a human, gets tested in a throwaway copy, and only then becomes a report and a ready-to-review patch.

Who does the work: code or AI?

A common assumption is that "the AI does the scanning" and the API is rented computing power. Neither is true here. The API is not a GPU or RAM rental: you send text to a model hosted by Anthropic and get text back. Your own computer does all the scanning, graph building, scoring, policy checks and testing.

The code is the detective's forensic lab: fingerprints, lab results, records. The AI is the detective reading the lab report and writing "this matters because…". Take the detective away and the lab still produces every result. That is what offline mode is.

In numbers: in a default run the AI looks at 8 of 58 findings (the highest-risk finding of each type) plus the plans you ask for. That keeps cost and time bounded, and the pipeline still works if the AI is unavailable.

Stage by stage

1 · Discover — "what is in the app?"

Write down every ingredient, who supplied it, and who that supplier got it from.

The Guardian reads package.json (what the developer asked for, e.g. "sanitize-html, any 1.x") and package-lock.json (what was actually installed, e.g. exactly 1.4.2, downloaded from this URL, with this sha512 fingerprint). To know who pulled in whom, it re-implements npm's lookup rule: when package A needs B, npm looks in A/node_modules/B, then each parent folder up to the root. That rebuilds the real tree, so any package can be traced back to the choice that introduced it.

It also reads every Dockerfile (base images, whether each is pinned to an immutable @sha256 digest, tools installed during the build, which user the container runs as) and every GitHub Actions workflow (which third-party actions run, pinned to a commit or a movable tag). Everything is written as a CycloneDX 1.6 SBOM, the industry-standard ingredient list.

guardian/discover.py · guardian/sbom.py · guardian/eco_pypi.py

2 · Detect — "what looks wrong?"

Check each ingredient against public recall lists, and look for signs of tampering that no recall list would catch yet.

Known vulnerabilities. All 2,111 name/version pairs are sent in batches of 250 to the GitHub Advisory Database via npm's bulk endpoint; Python packages use PyPI's vulnerability feed. Each advisory says which versions are affected, e.g. <2.0.0-beta. A small semver evaluator decides whether 1.4.2 falls in that range. Then, from the registry's full version list, the Guardian computes safe versions: versions that fall in no known advisory range.

3 · Score — "does it matter for this app?"

A recalled ingredient that sits unopened in the storeroom is less urgent than one that goes into tonight's main course.

The Guardian scans the app's own source for import/require of each package (tests excluded) and records which functions are used. Each finding then gets a score where every factor is visible:

risk = base severity (CVSS) × reachability × exposure × environment

reachability   imported by app code 1.0 · pulled in by an imported package 0.85
               not referenced 0.55 · dev / test only 0.3
exposure       network-facing server 1.0 · browser bundle 0.8
environment    production 1.0 · dev-only 0.4
malicious-type findings (typosquat, lockfile drift, bad install script) force all factors to 1.0:
they do damage at install time, whether or not the code is ever called.

Critical ≥ 9 · High ≥ 7 · Medium ≥ 4 · Low < 4

4 · Investigate, check, recommend — the AI layer

Investigator

Gets one finding plus its evidence. It can call five read-only tools: fetch evidence by ID, show dependency paths, find usages in code, look up registry history, read a source file (key files refused, secrets redacted). It ends by submitting a verdict where every claim is labelled verified fact (with evidence IDs) or inference.

Skeptic

Its only job is to find unsupported claims. First, code checks every cited ID exists in the ledger. Then the AI checks the cited records actually say what the claim says. A failed fact is downgraded to inference and confidence drops by 0.1.

Remediator

Code first builds a short list of allowed fixes: upgrade to a computed safe version, pin via npm overrides, replace a look-alike with the real package, digest-pin an image, block, escalate. The AI picks one and explains risk reduction, compatibility and rollback. A choice not on the list is rejected.

5 · Gate, approve, validate, report

Policy. Rules in policy/guardian.rego (Open Policy Agent) decide two things: whether the build is blocked (typosquats, lockfile tampering, critical reachable bugs, malicious install scripts) and whether a fix may enter the sandbox (only with a recorded human approval and a target from the allowed list). auto_merge_allowed := false has no override.

Validation copies the repo into a sandbox with its own git history, applies the change, re-resolves the lockfile with --ignore-scripts (no third-party code runs), and rescans with the full Day 1 pipeline. It reports whether the target finding is gone, whether any new finding appeared, and the total risk before and after. It also produces an SBOM diff and an API compatibility probe: install old and new versions side by side, list what each exports, and check whether anything this app uses has disappeared.

Output is a git patch plus a pull-request description with evidence, results and rollback steps. A human reviews and merges it.

One finding's journey: sanitize-html

This is the Day 2 demo question, "take a finding from detection to verified remediation", traced through real output from the Juice Shop run.

  1. Discovered

    package.json pins sanitize-html to 1.4.2. Path: juice-shop → sanitize-html@1.4.2, a direct dependency.

  2. Detected

    The advisory database returns several matches for 1.4.2, including GHSA-qhxp-v273-g94h (XSS, CVSS 6.1, affects <2.0.0-beta) and a ReDoS advisory. Each is stored as a ledger record.

  3. Reachable

    Imported in lib/insecurity.ts:13 and lib/challengeUtils.ts:5, and called as a function. Reachability factor 1.0.

  4. Scored

    7.5 × 1.0 × 1.0 × 1.0 = 7.5 → High. Ranked behind the two critical findings (jsonwebtoken, marsdb).

  5. Fix options computed

    Registry history shows 16 advisory ranges for this package. The lowest version outside all of them is 2.18.1; latest safe is 2.18.2. No safe 1.x exists, so this is a major-version jump and gets flagged as likely breaking.

  6. Planned

    Remediator: upgrade sanitize-html@2.18.1, status "awaiting approval". The policy gate refuses validation until a person runs approve F-018 --by <name>.

  7. Validated

    The sandbox applies the change, rebuilds the lockfile, rescans, diffs the SBOM, and runs the API probe (app uses the module as a callable; does 2.18.1 still export one?). The result is VERIFIED or NEEDS_REVIEW.

  8. Reported

    out/prs/F-018.patch and F-018.md: change, evidence IDs, before/after risk, compatibility note, rollback (git revert). Merged by a human or not at all.

The hallucination guard

Language models can state wrong things confidently. The design does not ask the model to be careful. It makes unsupported statements visible and keeps them from deciding anything.

Four more protections sit around the agents:

  • Closed action space: the Remediator cannot invent a version number. Its choice must match a code-computed candidate.
  • Untrusted-data fencing: package descriptions, install scripts and source code reach the model inside <untrusted_data> tags, and the system prompt says to treat them as data. This guards against a malicious package whose description says "ignore previous instructions".
  • Read-only tools with secret filtering: Juice Shop ships encryptionkeys/premium.key. The read tool refuses such paths and redacts private keys and tokens from anything else.
  • Nothing runs, nothing ships: install scripts are never executed, nothing is published or pushed, and validation requires a named human.

Running it: Mac, Windows, with or without a GPU

No GPU is required. The heavy lifting is file parsing and web lookups, which take about 5 seconds and well under 1 GB of RAM for Juice Shop. An 8 GB M1 MacBook Air is plenty. A GPU matters only if you want the AI agents to run on your own machine instead of the Claude API.

Windows-specific handling in the code: files are always read and written as UTF-8, paths are stored with forward slashes, npm is resolved to npm.cmd, read-only git files are unlocked before the sandbox is deleted, and console output tolerates non-Latin characters.

Does it work on any repository?

Yes, for the ecosystems it has adapters for. Juice Shop is only the demo target; nothing in the detectors is specific to it. Pass any folder or Git URL:

python -m guardian.cli --out out-myrepo day1 --prepare --target https://github.com/owner/repo

--prepare generates missing npm lockfiles with install scripts disabled. Tested so far:

Supported today: npm (package-lock.json), Python (requirements*.txt, poetry.lock, uv.lock, Pipfile.lock), every Dockerfile, every GitHub Actions workflow. Not yet: Maven/Gradle, Go modules, Cargo, NuGet, yarn and pnpm lockfiles. Adding one means writing a new eco_<name>.py with three functions (discover packages into the graph, fetch advisories, find imports). The scoring, AI agents, policy, ledger and reports work unchanged, because they only see graph nodes and findings.

Known gap for Python: PyPI's feed does not include severity scores. The Guardian asks OSV, then GitHub; if neither responds (offline or rate-limited) severity shows as "unknown" and scores a flat 6.5.

How an engineer would build this without an AI assistant

The thinking is the same with or without an AI assistant, because the problem forces it. A security engineer would ask five questions in order. Each answer is a stage.

  1. "What did we actually ship?"

    The first instinct is to read package.json. The first lesson is that it lies: it lists ranges and only direct dependencies. The truth is in the lockfile, and the tree comes from how npm resolves node_modules. Off-the-shelf tool: Syft or cdxgen to produce an SBOM.

  2. "Which of these are known-bad?"

    Look each version up in a vulnerability database. Off-the-shelf: Grype, OSV-Scanner, Trivy, or npm audit. The lesson here: databases speak in version ranges, so semver comparison sits at the heart of it.

  3. "What attacks have no CVE yet?"

    Look at the attacks that made headlines: event-stream and flatmap-stream (a malicious update), ua-parser-js (a hijacked maintainer), the codecov bash uploader (curl | sh in CI), tj-actions (a movable tag on a GitHub Action). Each becomes a check: look-alike names, install scripts, lockfile drift, unpinned images and actions. Off-the-shelf: Socket, GuardDog, OpenSSF Scorecard.

  4. "Which of these should I fix first?"

    A raw scanner on Juice Shop prints dozens of issues, and teams ignore long lists. So rank them: is the package imported, by production code, in a service exposed to the network? This is where a human analyst would spend days, and where an AI model can help, as long as it cites what it saw.

  5. "Did the fix work, and did it break anything?"

    Apply the fix somewhere disposable, re-run the same scan, compare. Off-the-shelf: Renovate or Dependabot open the PR; OPA/Conftest enforces rules; cosign and SLSA verify provenance.

Same shape, a few different choices

A hand-built version would likely chain Syft → Grype → a script → Renovate. We kept the same order but wrote the core pieces ourselves for three reasons:

  • One evidence format. Gluing five tools means five output formats. Owning discovery and detection means every fact lands in one ledger with one ID scheme, which the AI can cite and an auditor can verify.
  • Reachability and parent constraints. Most scanners stop at "affected". We needed "imported where, using which functions, pulled in by whom, and does the parent's version range allow the fix".
  • A closed loop. Validation must rescan with exactly the detectors that raised the finding, or "fixed" means nothing.

Mistakes you would hit, because we hit them

  • Comparing @simplewebauthn/server by its last part flagged it as a typosquat of semver. Fix: compare full scoped names.
  • The app imports the top-level jsonwebtoken, which made a nested copy inside express-jwt look directly reachable. Fix: nested copies can't be reached by the app's own imports.
  • certifi@2022.12.7 looked like a suspicious version. Fix: recognise date-based versioning.
  • Windows reads files as cp1252 by default and runs npm as npm.cmd. Fix: explicit UTF-8 everywhere, resolve executables.

A realistic build order for a team of 3–4

Day 1 morning: lockfile parser and graph, SBOM output. Afternoon: advisory lookup, semver ranges, one non-CVE detector (typosquat), Dockerfile and workflow parsing. Evening: reachability scan, scoring, evidence ledger, Markdown report. Day 2 morning: agents with tools, the Skeptic, the candidate list. Afternoon: policy, approval, sandbox validation, diffs. Evening: rehearse the sanitize-html journey end to end.

Glossary

Dependency
A package your code uses. Direct if you asked for it; transitive if something you asked for needed it.
Lockfile
The exact record of what got installed: version, download URL and fingerprint for every package. Without it, two installs a day apart can differ.
SBOM
Software Bill of Materials: an ingredient list in a standard format (CycloneDX, SPDX) that other tools can read.
CVE / GHSA
Public IDs for a known vulnerability. CVE is the global catalogue; GHSA is GitHub's advisory ID, often linked to a CVE.
CVSS
A 0–10 severity score for a vulnerability in general, not for your app. That is why the Guardian adjusts it.
Reachability
Whether your code actually uses the vulnerable package (and which parts of it).
Typosquatting
Publishing a package with a name one typo away from a popular one, hoping someone installs it by mistake.
Dependency confusion
Publishing a public package with the same name as a company's internal one and a very high version number, so tools pick the attacker's.
Install script
Code a package runs automatically during npm install. Useful for compiling; dangerous if malicious.
Image digest
An unchangeable fingerprint (@sha256:…) for a container image. A tag like node:24 can be re-pointed; a digest cannot.
SHA pinning
Referring to a GitHub Action by commit hash instead of a tag, for the same reason.
OPA / Rego
Open Policy Agent, a standard engine for writing security rules as code that a machine enforces.
Hash chain
Each record includes a fingerprint of the previous one. Changing an old record breaks every fingerprint after it.
Tool use
Letting an AI model call functions you provide (here: read-only lookups) and see the results before answering.
Hallucination
When an AI states something false with confidence. Handled here by requiring citations that are checked.

Known limitations

  • Reachability works at the import level, not by tracing individual function calls.
  • Ecosystems: npm and PyPI. Maven, Go, Cargo, NuGet, yarn and pnpm need adapters.
  • Digest pinning needs registry access to look up the sha256; the plan records the command.
  • Full unit tests in the sandbox are optional (--run-tests), since a complete Juice Shop install includes an Angular build.
  • Tested in this build: Day 1, planning, the approval gate, the tamper scenario, the Python adapter, URL targets with --prepare, and the local-model code path against a mock server. Still to test: sandbox validation after a real approval, live Claude calls, a real Ollama model, and the Windows scripts on Windows.
