0 · Opening 30 seconds

“Modern applications are mostly assembled, not written. Our target, OWASP Juice Shop, has 161 packages its developers chose, but it actually ships with 2,111. The other 1,950 came in automatically because those packages needed them. Day 1 answers three questions: what's really inside, what changed, and what looks risky. Every answer comes with evidence we can point to.”
“One principle runs through everything. Plain code collects every fact. The AI is only allowed to reason about facts the code has already recorded, and it has to cite them. That's how we prevent made-up answers.”

1 · Why this target repository 30 seconds

“We chose OWASP Juice Shop because it meets every requirement in the brief. It's free and open source. It's containerised with a multi-stage Dockerfile. It has 16 GitHub Actions workflows, so there's a real CI/CD pipeline to inspect. It has two npm projects, a Node server and an Angular frontend, with a realistic tree of direct and transitive dependencies. And it contains real supply-chain problems, including a typosquat.”
“The Guardian isn't hard-coded to Juice Shop. The same pipeline scanned PyGoat, a Python app, and Express, which doesn't even commit a lockfile.”

2 · Step 1: Discover components 1.5 minutes

“First we read every package manifest and lockfile. package.json is what the developer asked for, usually a version range. package-lock.json is what actually got installed: the exact version, the download URL, and a sha512 integrity hash for every package.”
“To know who pulled in whom, we re-implemented npm's resolution rule. When package A needs B, npm looks in A's own node_modules folder first, then walks up the parent folders to the root. Replaying that rule rebuilds the real dependency tree, so any package can be traced back to the decision that introduced it.”
“Juice Shop doesn't commit its lockfiles, so we generated them with npm install --package-lock-only --ignore-scripts. That resolves versions without running any package code.”
  • Lockfile v3 format; the dev, optional and hasInstallScript flags are kept for each package.
  • NetworkX directed graph: each node is a package at a lockfile path, each edge carries the version range the parent asked for.
  • Python projects go through a second adapter (eco_pypi.py) that reads requirements, poetry, uv and Pipfile files.
Run the scan and point at 2111 packages, 161 direct, 3 Dockerfiles, 16 workflows. 
python -m guardian.cli --out out-demo day1 --target targets/juice-shop --investigate 8

3 · Step 2: Build the supply chain view 1.5 minutes

“Everything goes into a CycloneDX 1.6 SBOM, the industry-standard software bill of materials. Each component has a package URL, its version, its integrity hash, where it was downloaded from, whether it's a dev dependency, and the full dependency relationships.”
“The brief asks us to inspect at least one container image or CI/CD workflow. We inspect all of them. For Dockerfiles: every base image, whether it's pinned to an unchangeable @sha256 digest or only a movable tag, tools installed during the build, and which user the container runs as. For GitHub Actions: every third-party action, whether it's pinned to a commit SHA or a tag someone could move, plus risky triggers like pull_request_target and curl | sh. These go into the SBOM too, because the build pipeline is part of the supply chain.”
Show the SBOM file. In the dashboard: Overview → Components 2,111 and Containers & CI: 5 base images, 94 actions. 
head -c 1500 out-demo/sbom.cdx.json

4 · Step 3: Detect known vulnerabilities 1.5 minutes

“We send all 2,111 name and version pairs, in batches of 250, to the GitHub Advisory Database through npm's bulk advisory API. Each advisory gives an affected version range such as <2.0.0-beta, and our semver evaluator checks whether the installed version falls inside it.”
“For each match we also compute fix candidates from the registry's full version history: the smallest safe version on the same major line, the smallest safe version overall, and the latest safe version. ‘Safe’ means it falls inside no known advisory range. We also record the parent's constraint, for example express-jwt requiring jsonwebtoken ~0.1.0. That tells us whether a simple refresh fixes it or the parent has to change too.”

6 · Step 5: Present evidence and initial risk 1.5 minutes

“For every finding we show the five things the brief asks for: what was detected, which component, its dependency path, the supporting evidence, and the initial risk level.”
“Risk isn't just CVSS. We scan the app's own source code for imports, excluding tests, to see whether the package is actually used and which functions it calls. A CVSS 9.8 bug in a test helper ranks below a 7.5 bug in code we actually call. Of 39 package findings, 23 are reachable by app code.”

“Every fact (an advisory, a registry lookup, an import found in code) is written to an evidence ledger with an ID like E-0142. Each record contains the SHA-256 hash of the one before it. Editing any past record breaks the chain. Our run has 268 records with the chain intact. On Day 2, the AI agents are only allowed to cite these IDs.”
“A policy written in Rego, Open Policy Agent's rule language, turns findings into a decision. Juice Shop is BLOCKED: two critical reachable vulnerabilities and one typosquat, plus 17 warnings.”
Dashboard → Findings → ngy-cookie: “Why this score”, “How it got into the app”, then the Evidence tab with the raw ledger records. Then Risk map: the graph of every risky package and its path into the app.

Likely judge questions

How is this different from npm audit?
npm audit lists CVEs. We add reachability, dependency paths with parent constraints, nine non-CVE attack checks, container and CI inspection, lockfile tampering detection, and tamper-evident evidence.
Did you run any package code?
No. Everything uses --ignore-scripts, and we only read files and registry metadata.
How do you avoid false positives?
We compare scoped names only with other scoped names, so @simplewebauthn/server isn't flagged as a fake semver. A nested copy of a package isn't counted as reachable just because the app imports the top-level copy. Date-based versions like 2022.12.7 aren't treated as anomalies.
Is reachability exact?
It works at the import level and records which functions are used. Function-level call-graph analysis is the next step, and saying that openly is a strength.
Where is the AI on Day 1?
Day 1 is deliberately plain code, so it's fast, reproducible and verifiable. The AI agents use these facts on Day 2. Without an API key they run in offline mode, which uses rules instead of a model.
Does it work on other repositories?
Yes: any npm or Python repo, plus every Dockerfile and GitHub workflow. Show the New scan page with a GitHub URL.
